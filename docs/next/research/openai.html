Spike: Claude Code's traffic on OpenAI's Responses API

Issue: #368 · Date: 2026-10-21 · Status: complete

Question​

Claude Code speaks the Anthropic Messages API. To let an OpenAI model answer it (FR-11), Janus has to translate each request into OpenAI's Responses API and each answer back. What carries over field by field, what cannot, what the prompt cache needs, and which models are candidates?

Method​

Nothing was sent to OpenAI: the owner has no account (charter D7). The mapping is built from three sources, all read on 2026-10-21:

  • OpenAI's published API reference and guides, in their Markdown form under developers.openai.com, listed under Sources. platform.openai.com refused the fetch (HTTP 403); the same pages are served from developers.openai.com.
  • The open-source Codex CLI, openai/codex at commit d138398cef (2026-10-21), as evidence of what a real client sends and how it reads the answers.
  • Janus's own record of what Claude Code sends: traffic.md, integrity.md, lmstudio.md, and internal/backend (Normalize, RepairForUpstream).

Where the docs say nothing, contradict themselves, or describe something only real traffic can confirm, the row is marked #399, the owner's validation sessions.

Decision​

The translation is feasible, and closer than expected: OpenAI's newer models cache with explicit breakpoints, up to four writes per request, much as Anthropic's do. The Codex CLI already sends what Janus should send. In short:

  • Every request goes with store: false, no previous_response_id, truncation: "disabled", stream as Claude Code asked, and the full translated history. That is exactly what the Codex CLI sends (codex-rs/core/src/client.rs, build_responses_request). It costs nothing extra in tokens: input is billed in full even when chaining with previous_response_id (conversation state).
  • Caching uses explicit mode on GPT-5.6 and later: each Anthropic cache_control becomes a prompt_cache_breakpoint on the same block, so the four breakpoints Claude Code places become OpenAI's four writes. prompt_cache_key is a hash of Claude Code's session id.
  • Candidates, defaults for #374 to confirm with the owner: gpt-6.1-sol for Opus and Sonnet requests, gpt-6-luna for Haiku, gpt-6-astra by choice. Effort maps one to one onto reasoning.effort, clamped to what the model accepts. The dedicated -codex models stop at gpt-5.3-codex, which has a 400k window, a 2025 knowledge cutoff, and no explicit cache breakpoints. Codex itself now recommends gpt-6.1-sol (Codex models).

Tool names and schemas​

  • The docs give no limit on a function's name. The only stated rule is for a response format's name: a-z, A-Z, 0-9, underscores and dashes, at most 64 characters (create). The Codex CLI replaces every character outside [A-Za-z0-9_] with _ and keeps names to 128 characters, adding a 12-character SHA-1 suffix when it has to shorten or two names collide (codex-rs/codex-mcp/src/mcp/mod.rs, sanitize_responses_api_tool_name; codex-mcp/src/tools.rs, MAX_TOOL_NAME_LENGTH).
  • What Claude Code sends: its own tools have plain names (Bash, Read, Edit, …). MCP tools are mcp__<server>__<tool>, and server names can hold dashes, as in mcp__claude-in-chrome__computer.
  • Decision: a name that matches ^[A-Za-z0-9_]{1,64}$ goes as it is. Any other is encoded: each other character becomes _, the result is cut to 51 characters, and _ and the first 12 hex characters of the SHA-1 of the original name are added. On the way back, a call's name is decoded from the tools in the same request, so no table is kept across turns or restarts. The 64-character limit is the stricter of the two documented rules, and whether OpenAI accepts dashes is #399.
  • Schemas go with strict: false. Strict mode needs additionalProperties: false on every object and every property required (fc). Claude Code's schemas have optional fields, and making them nullable-required would change what the tools accept. If strict is left out, Responses tries to convert the schema to strict itself, which could change it without notice. The Codex CLI sends strict: false for every tool (codex-rs/tools/src/responses_api.rs). The structured-outputs guide contradicts itself on whether pattern and format work in strict mode (structured outputs); with strict off it does not matter.

Tool search​

Claude Code's tool search is an ordinary tool (ToolSearch) whose result holds tool_reference blocks. The Anthropic API expands each one into the definition of a tool that was sent with defer_loading. OpenAI has a tool search of its own, but in it the model, not a client tool, asks for the search (tool search). So Janus does the expansion itself, in the history:

  1. Tools marked defer_loading are not sent in tools.
  2. A tool_result holding tool_reference blocks becomes a function_call_output with text naming each tool, as for LM Studio (#169). Straight after it comes an additional_tools item with the definitions of the tools named.

The result depends only on that point in the history, so each turn sends the same bytes. OpenAI loads tools at the point they appear in the input, which "allows the model's cache to be preserved from one request to another" (tool search). additional_tools items do not accept an explicit breakpoint (caching); the next message's breakpoint covers them.

Prompt cache​

What OpenAI's cache needs (caching):

  • The same rendered prefix. Anything changed before a breakpoint misses from there on. That covers model, tools (including order), parallel_tool_calls, reasoning.effort, and the text format.
  • A breakpoint. On GPT-5.6 and later, explicit breakpoints go on content blocks (input_text, input_image, input_file, and the parts of a function output), up to four writes per request, with the 2 first and 50 latest explicit breakpoints checked on lookup. In implicit mode OpenAI places one at the end of the latest eligible message. Earlier models, gpt-5.3-codex among them, cache only implicitly, at fixed intervals, helped by prompt_cache_key.
  • At least 1,024 visible tokens before the breakpoint on GPT-5.6 and later.
  • Prices on GPT-5.6 and later: a write costs 1.25 times uncached input for the default 30-minute lifetime and 2.5 times for 12 hours; a read 0.1 times (0.05 times on gpt-6.1-sol).

How the translation keeps it:

  • Determinism. Every rule above maps the same Anthropic history to the same bytes: no timestamps, no counters, no map iteration order, a string message always becoming the same block, and dropped blocks dropped every time. #372's test that turn N+1's prefix equals turn N's is the guard.
  • Breakpoints follow Claude Code's. Claude Code places at most four cache_control marks: two on the system blocks, one after the injected tool definitions, one moving along the tail (traffic.md). Each becomes an explicit breakpoint on the same block, in explicit mode, so OpenAI writes where Claude would and nowhere else. A mark on a block that is left out (the billing header, a thinking block) moves to the nearest earlier block that is kept.
  • Lifetimes. Claude's 5-minute and 1-hour marks both become "30m". A 1-hour mark could become "12h", at twice the write price. The reference allows only "30m", while the caching guide offers "12h" in the Responses API (create reference against caching): #399, and "30m" until then.
  • Effort stays put. A change of effort mid-conversation rewrites OpenAI's hidden instructions. GPT-6 models offer a configuration_update input item that changes effort without that (reasoning); Claude Code keeps one effort per session, so Janus does not need it yet.

The Responses stream is typed events with a sequence_number (streaming events). The Codex CLI dispatches on the type in each event's data (codex-rs/codex-api/src/sse/responses.rs), and Janus should too, not on the SSE event: line, whose presence the docs do not show (#399).

OpenAI's input_tokens includes cached and written tokens (caching), as LM Studio's does and Anthropic's does not. The four Anthropic input fields must add up to the true total, because Claude Code judges how full its context is from them. The ledger (#381) keeps OpenAI's own numbers and prices them with OpenAI's rates; the costs Claude Code shows for those turns will be wrong, since it prices them as Claude.

Errors​

Rate-limit headers​

OpenAI sends x-ratelimit-limit-, -remaining-, and -reset-requests and -tokens, sometimes project-scoped versions of the token headers, and Retry-After on a temporary 429 or 503 (rate limits). These differ from Anthropic's in two ways that matter to #378 and #382:

  • The limits are per minute. There is no five-hour or weekly usage as with Claude's subscription. The reset values are durations from now (1s, 6m0s), not times, so Janus converts them on receipt.
  • The limits that end a session have no reset. Credit, spend, and usage limits come back as 429 with a code and no reset header; they last until the owner acts or the month turns.

So on OpenAI, "return when the limit resets" applies to per-minute limits only, and those pass in seconds or minutes. A quota error takes OpenAI out of the chain until restart, and doctor says why.

Which models (#374). The owner asked for "Codex". The -codex line of models ends at gpt-5.3-codex, which is smaller, older, and caches only implicitly. The Codex CLI itself now points its users at gpt-6.1-sol (Codex models). Proposed defaults, to be confirmed with the owner:

Effort (#374). Claude Code's output_config.effort maps one to one onto reasoning.effort (low, medium, high, xhigh, max), clamped to the nearest value the model accepts (reasoning). Where a request gives a thinking budget instead, the budget picks the effort: under 4,000 tokens low, under 16,000 medium, under 32,000 high, otherwise xhigh. Thinking off becomes the model's lowest effort. These thresholds are a starting point, not a measurement.

Carrying reasoning back (#410)​

Without its earlier reasoning, an OpenAI model starts each turn's thinking from scratch. The docs recommend passing reasoning items back, at least those since the last user message, when calling tools (reasoning). It is possible statelessly:

  • With store: false, each reasoning item in output has encrypted_content, and sending the items back lets the model use them; GPT-5.6 and later do so on every turn by default (reasoning.context: "all_turns").
  • Reasoning carries only within one model family: gpt-5.6-sol and gpt-5.6-luna share, GPT-5.6 and GPT-5.5 do not. Items from another family are ignored, not rejected.
  • An item must be sent back as it came, with its id; the docs' own example keeps "every output item" (#399 for whether id is needed with store: false).
  • On GPT-5.5 and GPT-5.4, OpenAI also asks that each assistant message's phase (commentary or final_answer) be sent back, or a preamble may be taken as a final answer (reasoning).

Claude Code keeps the thinking blocks it is given, signature and all, and sends them back on later turns. integrity.md saw this with LM Studio's empty signatures. So a response's reasoning items, its messages' phase values, and the model family can travel in a thinking block's signature as a Janus envelope, for example janus-oai:1: and base64 of a small JSON object. Janus unpacks it on the way to OpenAI and drops the whole block on the way to Claude. RepairForUpstream today drops only empty signatures, so it must learn the envelope as well; otherwise Claude refuses the request. How large the encrypted content gets, and whether Claude Code keeps a very long signature intact, is #399.

What store: false costs​

  • In tokens, nothing. Input is billed in full whether the history is sent or chained with previous_response_id (conversation state), and the prompt cache works the same either way.
  • In bytes, the whole conversation each turn. That is what Claude Code already sends to Anthropic.
  • What it does not stop. OpenAI keeps abuse-monitoring logs of Responses traffic for up to 30 days whatever store says, unless the organization has Zero Data Retention or Modified Abuse Monitoring (your data). OpenAI says this traffic is not used for training. The threat model (#385) has to say so.

What this does not show​

  • Anything about real traffic. No request was sent. Every mapping is read from documentation and from the Codex CLI's source, which shows what OpenAI accepts from one client, not from Janus.
  • How well an OpenAI model drives Claude Code. Claude Code's system prompt says the model is Claude, and its tools are described for Claude. Whether gpt-6.1-sol follows them well is untested.
  • Whether Claude Code accepts every answer shape. In particular, an Anthropic stream with zero usage at the start and the full usage at the end, very long signatures, and the error wording it reacts to.
  • The open points marked #399:
    • which tool names OpenAI accepts
    • whether the "12h" cache lifetime is accepted
    • whether the SSE event: line is present
    • what /v1/responses/input_tokens costs
    • whether reasoning items need their id with store: false
    • how large the reasoning envelope gets
  • Prices and models that change. Everything here is as of 2026-10-21; one price is marked promotional. The pricing table in #381 is to be dated and checked when it is written.
